## MISSÃO DE IMPLEMENTAÇÃO: v0.5 BACKEND INSTITUCIONAL

Não fique apenas analisando ou produzindo plano. Depois da auditoria, abra uma branch própria, preferencialmente:

`feat/v0.5-backend-institucional`

E implemente o backend institucional sobre o núcleo v0.4 já comprovado.

### 1. Supabase dedicado
- Verifique os projetos conectados.
- NÃO reutilize RADAR PDDE, CTRH, PDDE Online antigo ou qualquer banco de outro sistema.
- Crie/vincule um Supabase exclusivo deste projeto, com nome inequívoco como `pdde-repasse-conciliador`.
- Revise e aplique `supabase/migrations/20260813050000_evidence_events.sql` nesse banco.
- Valide `verify_evidence_chain()` no Postgres real.
- Se houver uma autorização humana que a ferramenta realmente não possa dar, peça apenas essa autorização específica e continue o restante que for possível.

### 2. Persistência Postgres real
Implemente um `PostgresEvidenceStore`/`SupabaseEvidenceStore` que satisfaça o mesmo contrato do JSONL:
- append controlado;
- listagem por execução;
- listagem por escola;
- integridade da cadeia;
- erros claros;
- nenhuma mutação UPDATE/DELETE de eventos.

Mantenha SDK Supabase no adaptador, não no domínio. Crie testes de contrato compartilhados entre JSONL e Postgres quando fizer sentido.

### 3. Artefatos institucionais
Implemente uma porta de armazenamento e adaptador Supabase Storage (ou solução equivalente justificável) para HTML bruto, JSON/manifest, Excel e demais evidências relevantes.
- preservar SHA-256 e metadados;
- caminho estável por `runId`;
- `ARTIFACT_PRESERVED` apontando para o artefato institucional;
- nunca expor `service_role` ao cliente.

### 4. Serviços/read models
Exponha casos de uso eficientes para futura UI:
- lista das 163 escolas;
- escola por INEP;
- histórico da escola;
- lista/detalhe de execuções;
- achados e exceções;
- artefatos e relatório.

O log append-only continua sendo a verdade. Read models materializados, se necessários, devem ser projeções reconstruíveis.

### 5. API
Implemente contratos de API no runtime mais adequado ao projeto depois de verificar os limites atuais de deploy. Conjunto mínimo desejado:

- `GET /api/health`
- `GET /api/meta`
- `GET /api/schools`
- `GET /api/schools/:inep`
- `GET /api/schools/:inep/history`
- `GET /api/schools/:inep/findings`
- `GET /api/executions`
- `GET /api/executions/:runId`
- `GET /api/findings`
- `GET /api/executions/:runId/artifacts`
- endpoint seguro de relatório/download
- `POST /api/executions/pddeinfo`
- `POST /api/reconciliations`

Não rode uma coleta das 163 escolas dentro de uma requisição curta se o runtime não suportar. A API deve poder retornar um `runId` e a execução longa ocorrer em worker/job/runner apropriado. Verifique as limitações atuais da plataforma antes de escolher o mecanismo.

### 6. Orquestração
Crie a camada que:
- inicia execução;
- registra `EXECUTION_STARTED`;
- executa coleta/conciliação existente;
- persiste progresso, tentativas e artefatos;
- encerra `COMPLETE`, `PARTIAL` ou `FAILED`;
- permite consulta/polling;
- usa idempotência onde houver risco de duplicação acidental.

### 7. Segurança proporcional
- nada de `service_role` no frontend;
- escrita somente pelo backend/runner confiável;
- RLS coerente;
- endpoints de comando protegidos;
- sem overengineering de IAM neste momento;
- dados são públicos, mas operações administrativas não precisam ser públicas.

## INVARIANTES FINANCEIROS OBRIGATÓRIOS

Nunca viole:
- PDDEInfo `Valor Pago` NÃO é crédito bancário confirmado.
- Pagamento, OB, crédito, extrato direto e achado do `CONCILIADOR` são fatos distintos.
- Ausência não é zero.
- Histórico não preenche automaticamente conta corrente ausente.
- Conta de um programa não completa silenciosamente outro.
- Similaridade de valor sozinha não confirma correspondência.
- Cobertura insuficiente => inconclusivo.
- CAPTCHA não será contornado.
- Dinheiro crítico em centavos inteiros.
- Eventos de evidência são append-only.
